# АРХІТЕКТУРА ТА СПЕЦИФІКАЦІЯ СУМІСНОСТІ VOLNOST
## Принцип неагресивного поширення та міжоперабельності з екосистемами

> **Статус:** РОБОЧІ ЦІЛІ ДИЗАЙНУ (DESIGN TARGETS) — ПОТРЕБУЄ ЮРИДИЧНОГО АНАЛІЗУ.  
> **Методологічне правило:** Сумісність не є встановленим емпіричним фактом до моменту остаточного юридичного аналізу та складання точного тексту ліцензії. Усі оцінки в цьому документі є архітектурними цілями (`DESIGN TARGETS`), а не доведеною реальністю.

---

### 1. ТРИ НЕЗАЛЕЖНІ ВИДИ СВОБОДИ В ДИЗАЙНІ VOLNOST

Ми розмежовуємо три принципово різні площини свободи, які не повинні штучно змішуватися в одне положення:

```text
1. FREEDOM OF THE CODE (Свобода коду)
   └── Що дозволено робити з самою програмою (run, study, modify, distribute).

2. FREEDOM OF COMPOSITION (Свобода композиції)
   └── З яким іншим кодом її можна поєднувати без примусового переліцензування сусідів.

3. FREEDOM OF PERSONS (Свобода людини / Права і вольності)
   └── Які фундаментальні права людини та захист від агресії/тиранії є непорушними.
```

Ці три виміри не обов'язково мають реалізовуватися єдиною copyright restriction clause.

### 2. ДВОШАРОВА АРХІТЕКТУРА: COPYRIGHT LAYER ТА PACTA LAYER

Щоб уникнути нерозв'язного конфлікту між відкритістю коду та нормативними зобов'язаннями, розглядається розділення на два функціональні шари:

```text
                 VOLNOST
                    │
          ┌─────────┴─────────┐
          │                   │
   COPYRIGHT LAYER       PACTA LAYER
          │                   │
     file-local            normative
     copyleft              principles
          │                   │
          ▼                   ▼
 MIT / BSD / Apache       rights & liberties
 MPL / LGPL / GPL         research
 AGPL compatibility
```

1. **Copyright Layer (Юридична форма ліцензії):**
   - Проєктується максимально дружнім до композиції (OSI/GPL-friendly).
   - Забезпечує захист вихідного коду без накладання несумісних технічних обтяжень на компіляцію, лінкування чи використання в інших відкритих проєктах.
2. **PACTA Layer (Нормативний Пакт прав і вольностей):**
   - Нормативна угода сторін щодо взаємних зобов'язань, непідкорення сваволі та збереження свобод.
   - **Відкрите дослідницьке питання для юристів:** Чи повинен PACTA normative layer взагалі бути прямим copyright-use restriction (що автоматично конфліктує з OSD #5, #6 та GPL §10), чи він має діяти через інший юридичний інструмент (публічний договір, ковенант, статут спільноти)?

### 3. ФУНДАМЕНТАЛЬНИЙ ПРИНЦИП: НЕЗАЛЕЖНІСТЬ СУСІДНЬОГО КОДУ

В архітектурі взаємодії з іншими компонентами діє правило:

> **«Independent Code remains under its own terms solely by reason of combination with Covered Code.»**  
> *(Сусідній незалежний код зберігає власні умови і не підлягає примусовому переліцензуванню лише внаслідок поєднання з Covered Code).*  
> *(Внутрішня архітектурна мнемоніка: «не захоплювати сусідів»).*

```text
    ┌────────────────────────────────────────────────────────┐
    │                      LARGER WORK                       │
    │                                                        │
    │  ┌──────────────────────┐    ┌──────────────────────┐  │
    │  │  VOLNOST Covered     │    │  Незалежний сусідній  │  │
    │  │  Code (файли / модулі│    │  код (MIT / Apache / │  │
    │  │  під VOLNOST)        │    │  GPL / Proprietary)  │  │
    │  └──────────┬───────────┘    └──────────┬───────────┘  │
    │             │                           │              │
    │             ▼                           ▼              │
    │    VOLNOST-умови               Зберігає власну         │
    │    діють для файлу             вихідну ліцензію        │
    └────────────────────────────────────────────────────────┘
```

### 4. АНАЛІЗ НАПРУГИ З OPEN SOURCE DEFINITION ТА GPLv3

Напруга між широкою сумісністю та правами і вольностями **не є розв'язаною автоматично**:

```text
Широка сумісність з OSI / GPL
             ▲
             │  TENSION (Ідентифіковано, досліджується мінімізація)
             ▼
Обмеження дій / захист вольностей
```

1. **Конфлікт з OSD #5, #6:** Якщо ліцензія забороняє певні сфери використання коду, вона не може отримати статус OSI Open Source.
2. **Конфлікт із GPLv3 §10:** GPLv3 забороняє будь-які «further restrictions». Якщо умова про захист вольностей діє як copyright restriction, поєднання такого коду з GPL-кодом породжує юридичну несумісність.
3. **Механізм Secondary Licenses (урок MPL 2.0) та його реальна ціна:**
   - Прецедент MPL 2.0 показує, що міст до GPL працює лише тому, що автор прямо дає дозвіл поширювати Covered Code у складі Larger Work під GPL.
   - **Невідворотний наслідок:** При спрацьовуванні такого шлюзу ліцензія **мусить явно поступитися частиною власних специфічних обмежень**. Якщо код переходить під чисту GPLv3, специфічні заборони VOLNOST для цієї GPL-копії більше не можуть діяти, інакше порушується §10 GPLv3.
   - **Фундаментальне відкрите питання:** *Що для VOLNOST важливіше: щоб її власні нормативні умови супроводжували код абсолютно завжди (ризик гетто несумісності), чи щоб код міг вільно входити в глобальні екосистеми через Secondary License?*

### 5. МАТРИЦЯ ЦІЛЕЙ СУМІСНОСТІ (DESIGN TARGETS MATRIX)

Статуси матриці:
- `LIKELY ACHIEVABLE` — висока ймовірність реалізації на базі перевірених практик (file-level copyleft).
- `TARGET` — цільова орієнтація дизайну, яка потребує юридичної перевірки взаємодії умов.
- `CONDITIONAL` — сумісність можлива лише за умови явного механізму Secondary Licenses (із відмовою від конфліктних вимог у GPL-режимі).
- `CONFLICT / UNKNOWN` — пряма несумісність або невизначений правовий статус.

| VOLNOST + цільова ліцензія | 1. Включення в один проєкт (Side-by-side) | 2. Збірка в один binary (Linking) | 3. Копіювання коду між файлами (Merge) | 4. Похідний твір (Larger Work) | 5. Повне переліцензування (Relicensing) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **MIT** | `LIKELY ACHIEVABLE` | `LIKELY ACHIEVABLE` | `CONDITIONAL` (збереження ліцензії файлу) | `LIKELY ACHIEVABLE` (Larger Work під MIT, файл під VOLNOST) | `CONFLICT` (VOLNOST не перетворюється на MIT) |
| **BSD (2/3-clause)** | `LIKELY ACHIEVABLE` | `LIKELY ACHIEVABLE` | `CONDITIONAL` (збереження notice) | `LIKELY ACHIEVABLE` | `CONFLICT` |
| **Apache-2.0** | `TARGET` | `TARGET` | `TARGET` (потрібен аналіз patent/NOTICE взаємодії) | `TARGET` | `CONFLICT` |
| **MPL-2.0** | `TARGET` (як інженерний прецедент) | `TARGET` | `TARGET` (на рівні файлів) | `TARGET` (не «повний ізоморфізм», а спільна file-level концепція) | `CONFLICT` |
| **LGPLv3** | `TARGET` | `TARGET` | `NEEDS BRIDGE ANALYSIS` | `CONDITIONAL` (за наявності Secondary License) | `CONDITIONAL` (у складі Larger Work) |
| **GPLv3** | `TARGET` | `CONDITIONAL` (Secondary License) | `NEEDS BRIDGE ANALYSIS` | `CONDITIONAL` (Secondary License у складі Larger Work) | `CONDITIONAL` (через Secondary License) |
| **AGPLv3** | `TARGET` | `CONDITIONAL` (Secondary License) | `NEEDS BRIDGE ANALYSIS` | `CONDITIONAL` (Secondary License у складі Larger Work) | `CONDITIONAL` (через Secondary License) |
| **Proprietary / Commercial** | `LIKELY ACHIEVABLE` (side-by-side) | `CONDITIONAL` (якщо Covered Code відкритий) | `CONFLICT` (закритий код не може асимілювати VOLNOST) | `CONDITIONAL` (досяжно, якщо межа Covered Code це дозволяє) | `CONFLICT` |

### 6. СІМ ІНВАРІАНТІВ ДИЗАЙНУ ДЛЯ ЮРИДИЧНОГО АНАЛІЗУ

1. **C-INV-1 (Independent Code Standing):** *Independent Code remains under its own terms solely by reason of combination with Covered Code.*
2. **C-INV-2 (Local Scope):** Зобов'язання щодо копілефту та розкриття коду проектуються суворо для `Covered Code` (на рівні файлів/модулів).
3. **C-INV-3 (Larger Work Permissiveness):** Прямо передбачити право створення та розповсюдження комбінованих робіт (`Larger Works`).
4. **C-INV-4 (Explicit Secondary Licenses):** Дослідити конструкцію вторинних ліцензій (GPLv2+, GPLv3+, LGPLv3+, AGPLv3+) та визначити точний перелік умов VOLNOST, які поступаються місцем умовам GPL при активації шлюзу.
5. **C-INV-5 (GPL Bridge Due Diligence):** Спроєктувати механізм сумісності з GPLv3 так, щоб уникнути порушення заборони «further restrictions» за §10 GPLv3.
6. **C-INV-6 (Zero Administrative Overhead):** Не створювати обов'язкових реєстрацій, повідомлень розробників, звітів чи платних дозвільних процедур.
7. **C-INV-7 (Anti-Collision):** Уникати будь-яких процедурних суперечностей із фундаментальними положеннями екосистемних ліцензій (attribution, disclaimer of warranty, limits of liability).
