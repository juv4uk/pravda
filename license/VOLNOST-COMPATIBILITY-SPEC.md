# АРХІТЕКТУРА ТА СПЕЦИФІКАЦІЯ СУМІСНОСТІ VOLNOST
## Принцип неагресивного поширення та міжоперабельності з екосистемами

> **Статус:** Робоча архітектурна специфікація для проєктування `VOLNOST` та інструкцій юридичному раднику.  
> **Головна мета дизайну:** Максимальна композиційна сумісність із permissive (MIT, BSD, Apache-2.0), weak-copyleft (MPL-2.0) та strong-copyleft (LGPL, GPLv3, AGPLv3) екосистемами без втрати власного нормативного ядра.

---

### 1. ФУНДАМЕНТАЛЬНИЙ ПРИНЦИП: «НЕ ЗАХОПЛЮВАТИ СУСІДІВ»

Замість ідеології «вірусного» copyleft, що вимагає переліцензування будь-якого коду, який доторкнувся до твору, `VOLNOST` спирається на принцип **локального захисту**:

```text
    ┌────────────────────────────────────────────────────────┐
    │                      LARGER WORK                       │
    │                                                        │
    │  ┌──────────────────────┐    ┌──────────────────────┐  │
    │  │  VOLNOST Covered     │    │  Незалежний сусідній  │  │
    │  │  Code (файли / модулі│    │  код (MIT / Apache / │  │
    │  │  під VOLNOST)        │    │  GPL / Proprietary)  │  │
    │  └──────────┬───────────┘    └──────────┬───────────┘  │
    │             │                           │              │
    │             ▼                           ▼              │
    │    VOLNOST-умови               Зберігає власну         │
    │    діють непорушно             вихідну ліцензію        │
    └────────────────────────────────────────────────────────┘
```

> **Нормативне формулювання принципу:**  
> *«Вольності щодо VOLNOST Covered Code не можуть бути відібрані чи звужені, але сусідній незалежний код не стає VOLNOST лише через факт поєднання чи включення у спільну збірку (Larger Work).»*

---

### 2. НАПРУГА З OPEN SOURCE DEFINITION (OSD) ТА ЇЇ РОЗВ'ЯЗАННЯ

Існує об'єктивна правова напруга між двома цілями:

```text
Широка сумісність з OSI / GPL
             ▲
             │  TENSION
             ▼
Обмеження сфер використання (use restrictions)
```

1. **Вимога OSI (OSD #5, #6):** Забороняє будь-яку дискримінацію за особами, групами чи сферами діяльності (*«No Discrimination Against Fields of Endeavor»*). Будь-яка пряма заборона використання софту (навіть для агресивної війни чи репресій) автоматично виводить ліцензію за межі OSI-approved Open Source.
2. **Вимога GPLv3 (§10):** *«You may not impose any further restrictions on the exercise of the rights granted or affirmed under this License.»* Будь-які додаткові етичні чи поведінкові заборони роблять ліцензію несумісною з кодом під чистою GPL.
3. **Архітектурне рішення:**
   - **Не накладати довільних обмежень на технологічне використання в самому копірайтному гранті.**
   - Розмежувати:
     - **Технічний ліцензійний грант (Code License / Covered Code):** діє за моделлю *file-level copyleft* (MPL-подібно), що гарантує сумісність із бінарними збірками та іншими ліцензіями.
     - **Нормативний Пакт (PACTA):** етично-правова рамка взаємних зобов'язань сторін, яка не навішує несумісних технічних обтяжень на downstream-компіляцію та лінкування незалежних бібліотек.

---

### 3. МОДЕЛЬ SECONDARY LICENSES ТА ПЕРЕЛІЦЕНЗУВАННЯ (BRIDGE ДО GPL-FAMILY)

Як показав прецедент Mozilla Public License 2.0 (§1.12, §3.3), пряма співпраця з GPL досягається не сподіваннями, а **явним шлюзом вторинних ліцензій (Secondary Licenses)**:

```text
VOLNOST Covered Code
         │
         │ при включенні у Larger Work під GPLv3 / LGPLv3 / AGPLv3
         ▼
Дозволено додатково поширювати у складі такого Larger Work
під умовами відповідної Secondary License (GPL-family),
за умови що первинний код зберігає власні notice про VOLNOST.
```

Це дозволяє уникнути license proliferation і дає змогу розробникам вільно поєднувати VOLNOST-компоненти у великих Linux/GPL проєктах.

---

### 4. МАТРИЦЯ СУМІСНОСТІ ЗА ТИПАМИ ОПЕРАЦІЙ

Термін «compatible» не є атомарним. Сумісність досліджується окремо для кожного виду інтеграції:

| VOLNOST + цільова ліцензія | 1. Включення в один репозиторій / проєкт (Side-by-side) | 2. Збірка в один binary (Static/Dynamic Linking) | 3. Копіювання коду між файлами (In-file code merge) | 4. Створення похідного твору (Derivative Work) | 5. Повне переліцензування (Relicensing) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **MIT** | **ТАК** | **ТАК** | **ТАК** (якщо файл лишається під VOLNOST) | **ТАК** (Larger Work під MIT, Covered Code під VOLNOST) | **НІ** (VOLNOST не стає MIT) |
| **BSD (2/3-clause)** | **ТАК** | **ТАК** | **ТАК** (зі збереженням BSD notices) | **ТАК** | **НІ** |
| **Apache-2.0** | **ТАК** | **ТАК** | **ТАК** (зі збереженням NOTICE) | **ТАК** | **НІ** |
| **MPL-2.0** | **ТАК** | **ТАК** | **ТАК** (на рівні окремих файлів) | **ТАК** (ідеальний ізоморфізм на рівні файлів) | **НІ** |
| **LGPLv3** | **ТАК** | **ТАК** | Потребує сумісного шлюзу | **ТАК** (через механізм Secondary License) | Через Secondary License у складі Larger Work |
| **GPLv3** | **ТАК** | **ТАК** (через Secondary License bridge) | Потребує сумісного шлюзу | **ТАК** (у складі Larger Work під GPLv3) | Через Secondary License для всього твору |
| **AGPLv3** | **ТАК** | **ТАК** (через Secondary License bridge) | Потребує сумісного шлюзу | **ТАК** (у складі Larger Work під AGPLv3) | Через Secondary License для всього твору |
| **Proprietary / Commercial** | **ТАК** (side-by-side) | **ТАК** (якщо Covered Code залишається відкритим) | **НІ** (комерційний закритий код не може ковтати код VOLNOST) | **ТАК** (Larger Work може бути комерційним, але змінені файли VOLNOST публікуються) | **НІ** |

### 5. СІМ ІНВАРІАНТІВ СУМІСНОСТІ (VOLNOST-COMPATIBILITY INVARIANTS)

Юридичному раднику при складанні остаточного драфту ліцензії ставляться наступні 7 вимог:

1. **C-INV-1 (No Imperialism):** Не вимагати автоматичного переліцензування незалежного коду третіх сторін.
2. **C-INV-2 (Local Scope):** Зберігати вимоги відкриття та незмінності умов виключно для `Covered Code` (на рівні файлів/модулів).
3. **C-INV-3 (Larger Work Permissiveness):** Прямо дозволяти створення та розповсюдження `Larger Works`, що поєднують `Covered Code` з кодом під іншими ліцензіями.
4. **C-INV-4 (Explicit Secondary Licenses):** Чітко визначити перелік вторинних ліцензій (GPLv2+, GPLv3+, LGPLv3+, AGPLv3+) для легітимного комбінування зі strong-copyleft екосистемами.
5. **C-INV-5 (GPL Bridge):** Передбачити однозначний юридичний шлях розповсюдження у складі GPL Larger Work, який не створює ризику «further restrictions» за §10 GPLv3.
6. **C-INV-6 (Zero Red Tape):** Не створювати зайвих бюрократичних вимог: реєстрації розробників, спеціальних звітів, обов'язкових платних ліцензійних агентств тощо.
7. **C-INV-7 (Anti-Collision):** Не вводити жодних процедурних умов, які прямо конфліктують із базовими положеннями цільових open-source ліцензій (attribution, disclaimer of warranty).
